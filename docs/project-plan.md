# 專案規格草案

更新日期：2026-10-04（Asia/Taipei）。已確認上市＋上櫃普通股、五項條件全部通過、不足 20 檔不補、2 人 LINE 群組，以及下列財報、技術、法人、排序、起漲事件與績效定義。此文件保留完整目標設計；目前實作與驗收界線見 deployment.md。

## 1. 每日流程

1. GitHub Actions 每天 21:07 預定啟動，並提供手動補跑。相容的 UTC cron 為 `7 13 * * *`。
2. 決定台灣交易日期；非交易日不產生新推薦。週末仍可能補齊舊資料，但預設不另發 LINE。
3. 收集上市／上櫃證券名單、日 OHLCV、三大法人、已公開財報、月營收及公司行動資訊。
4. 驗證日期、欄位、單位、完整度與資料可用時間，保存來源與取得時間。
5. 更新指標與既有推薦績效，篩選當日候選股票。
6. 排序，產生最多 20 檔報告；符合不足 20 檔時不自動放寬門檻。
7. 先保存推薦與報告，再發送 LINE。保存發送狀態與重試鍵。
8. 保存本次執行摘要，列出資料缺漏、推薦數量、到期績效與發送結果。

21:07 是啟動時間，資料處理及發送會在之後完成。若排程延遲到隔日，使用排定交易日或明確指定的補跑日期，不能默默改為隔日推薦。

## 2. 已確認的篩選條件

| 項目 | 已確認第一版定義 | 邊界與後續可研究項目 |
|---|---|---|
| 範圍 | 已確認上市＋上櫃普通股，排除 ETF、權證、興櫃 | 以官方普通股分類識別，不能只看代號長度 |
| 財報 | 最近已公布的同口徑累計 EPS > 0；月營收近三個月合計較去年同期成長；現金流與利潤率列報告供觀察 | 現金流不是入選門檻；不同產業的利潤率分開解釋 |
| KD | 日 KD(9,3,3)：K≤D 且 0≤D−K≤3、差距較前一交易日縮小；或當天黃金交叉；或 K>D 且 K、D 均較前一交易日上升，不限交叉後天數 | rules-v4-kd-rising-top20；上升為 K今日>K前一交易日、D今日>D前一交易日，持平或下降不通過交叉後條件；不限低檔，交叉前僅代表接近，不保證未來交叉，不讀未來行情 |
| MACD | EMA(12,26,9)，今天 DIF > DEA，且最近三個交易日 DIF 逐日上升 | 三日數值需滿足 DIF(t) > DIF(t-1) > DIF(t-2)；不額外要求 DIF > 0 |
| 法人 | 外資＋投信＋自營商的合計淨買超，連續三個市場交易日均 > 0 | 採合計值，不要求三類各自都買超；自營商自行與避險不可重複加總 |
| 成交量 | 當日官方成交股數 >= 2,000,000 股，即 2,000 張 | 採官方日報表的成交範圍，不混用張與股 |
| 條件組合 | 已確認五項全部通過，不足 20 檔不補 | 不自動放寬門檻 |

財報與月營收是兩種不同頻率的資訊，明細各自保存在推薦紀錄。手機報告的入選名單只顯示排名與名稱。營收成長只是候選條件，並不代表未來獲利或股價一定上升。

金融業報表口徑不同，不能直接套用一般業的營業利益與現金流解釋。第一版 EPS 與營收為硬門檻，利潤率與現金流僅供觀察；須依產業識別欄位，未提供的觀察欄位標示無資料。缺硬門檻必要欄位時標示 `DATA_INCOMPLETE`，並揭露影響數量，不能補零或默默讓股票通過。

KD 的 RSV = 100 × (收盤－9 日最低價) / (9 日最高價－9 日最低價)，K、D 以 1/3 平滑並從 50 起算。分母為零時沿用前一 RSV（第一個值為 50）。MACD EMA 以固定最近 120 個連續有效交易日的第一個收盤起算；初始化方法、暖機長度與版本固定。完整目標須處理公司行動造成的價格跳動；當前實作為未還原日價格，限制在報告與部署指南揭露。

## 3. 排名與「機率」的區別

第一版採用已確認的透明、可重現排序：

1. 最近三日合計法人淨買超股數／同期成交股數，降冪。
2. 近三個月合計營收年增率，降冪。
3. MACD DIF 三日變化／當日收盤價，降冪。
4. 股票代號升冪，作為固定同分順序。

以上為逐項排序，不是經驗證的勝率模型。報告應列出觸發條件與數值，不能把任意總分轉成「有 80% 起漲機率」。排序與門檻一旦確認便版本化；後續調整保留舊版本，避免事後改寫結果。

已確認研究事件為「下一交易日開盤至第 10 個交易日收盤，价格報酬 >= 5%」。這是未來驗證的固定目標，不是現成機率模型。使用當時可取得的資料與當時完整股票範圍，分開研究、驗證與未見過的測試期間，評估樣本量、機率校準、基準差異及不同市場時期表現。

## 4. 資料來源與品質

優先評估證交所、櫃買中心與公開資訊觀測站的免費公開資料；不能只因有最新快照便假設具備完整歷史價格、法人、公告時間、現金流與公司行動。

- 上市資料入口：[TWSE OpenAPI](https://openapi.twse.com.tw/)。
- 上櫃資料入口：[TPEx OpenAPI](https://www.tpex.org.tw/openapi/)。
- 財報與公告：[公開資訊觀測站](https://mops.twse.com.tw/)。

實作前按資料類型確認端點、日期覆蓋、欄位、限流與使用／再散布條件。採全市場批次日資料與增量更新，避免每天逐檔重抓完整歷史。不加入未經確認的第三方替代來源。

每筆資料至少帶有 `source_date`、`fetched_at`、來源及內容雜湊；財報另存期間、公告或首次觀察可用時間。只使用推薦時已可取得的資訊。若官方沒有可靠歷史公布時間，不能宣稱已完成無未來資料的歷史回測；每日前瞻快照仍可累積驗證。

價格、法人或必要財報缺失時停止受影響範圍的排名，記錄品質失敗，不能將昨天資料包裝成今天的結果。交易日曆須識別假日與臨時休市，不能單純按星期一至五推算。

## 5. 每日紀錄與持久化

第一版使用 Python 與有版本的 JSON／gzip JSON 保存狀態；未使用 SQLite。GitHub Actions 每次都是新的環境，必須恢復與保存狀態。每日正式紀錄存到 repository 的專用資料分支，Actions artifact 僅供除錯備份，不能作為唯一永久資料庫。

| 資料 | 必要欄位 |
|---|---|
| 執行 | run_id、排定日期、實際時間、策略版本、程式版本、資料品質、狀態 |
| 推薦 | signal_id、交易日、市場、股票、名稱、排名、各條件數值、價格、資料版本 |
| 價格／來源 | 市場交易日、OHLCV、來源、取得時間、內容雜湊、調整依據 |
| 績效 | signal_id、持有期、基準日與價、到期日與價、原始報酬、成本假設、狀態 |
| 發送 | 報告日、群組識別的受控設定、payload 雜湊、retry key、結果 |

以市場＋股票＋推薦日期＋策略版本維持唯一推薦；同一股票連續入選可保留不同日期的訊號，但不能把重疊訊號當成獨立投資組合交易。重跑原報告預設只補缺失，不改寫推薦。

每天產生 reports/YYYY-MM-DD.md、該日推薦紀錄、績效更新及執行摘要。資料保存採先寫暫存再提交；避免一半更新，並以 workflow concurrency 防止同時修改。

LINE Token、Channel Secret、Group ID 使用 GitHub Secrets，不寫入程式、log 或公開資料分支。群組資訊不放在公開報告。

## 6. 績效定義

已確認主指標：推薦日 D 的下一個市場交易日開盤為基準，第 h 個推薦後市場交易日收盤為到期價，h ∈ {1,3,5,10,20}。第 1 日為下一交易日，因此 1 日報酬是該日開盤到收盤。

已確認以 5／20 個交易日提供約一週／約一月摘要，明確標示是交易日近似，不以曆週／曆月週年計算。

價格報酬 = 到期收盤價／基準開盤價－1。另可提供推薦日收盤到到期收盤的訊號觀察報酬，但兩者必須分開命名。

預設追蹤是訊號的價格觀察，不宣稱一定能以開盤價成交。停牌、無開盤價、漲停鎖住等執行限制須標記，不能虛構買入。到期日按市場日曆固定，不能為停牌股票偷偷往後延長持有期。

- `PENDING_ENTRY`：下一交易日還未到或基準價尚不可取得。
- `NOT_MATURE`：基準已確定，但持有期未到。
- `MATURE`：價格與必要調整可核驗。
- `MISSING_PRICE`／`SUSPENDED`：缺價或停牌，保留空報酬。
- `CORPORATE_ACTION_UNRESOLVED`：除權息、分割、合併、下市等影響尚未可核驗。

保留原始價格變化，只有公司行動資料完整時才另算含股息與股數變動的總報酬。手續費、賣出稅、滑價應在確認口徑與規則後獨立呈現，不能將不含成本結果稱為實際淨報酬。

每個持有期統計到期樣本數、有效數、未到期數、缺失數、平均與中位數報酬、正報酬比例，並做相同日期與價格口徑的市場基準比較。重複股票與重疊持有期會產生相關性，不能直接當成獨立樣本。

## 7. 免費資源邊界

GitHub：公開 repository 的標準 hosted runner 免費；私人 repository 的免費分鐘與儲存量依方案，另設執行時間、保留量與用量限制。排程可能延遲，公開 repository 60 日無活動時排程可能自動停用。使用手動補跑與保存摘要處理漏跑，不保證精準定時。

LINE 台灣輕用量方案目前月費 0 元，每月 200 則，不能加購。Push 按收件人數計算，同一 API request 內的 message objects 不另外增加計數。因此每天一次報告＋到期績效合併在同一 request，可避免額外發送次數。

估算月用量 = 報告天數 × 可收件人數 × 每日 request 數。本專案已確認 2 人群組：22 個交易日 × 2 人 × 1 次 = 44 則；即使 31 日每天一次也約 62 則。作為比較，22 個交易日 × 10 人 = 220 則，會超過免費額度。這些估算尚未包括測試、失敗後新發送及其他訊息，應保留餘額。

免費且每天發到 LINE 群組的可行性取決於實際人數與其他用量。若人數超標，需調整通知頻率或通知目的地，不能預設可永久免費。實際發送前查詢剩餘額度，不足時保留報告並記錄 `QUOTA_BLOCKED`。

Bot 必須允許加入群組，透過一次性的 webhook 設定取得 groupId。只做固定群組推播時，日常 GitHub job 可以直接呼叫 Messaging API，不需要常駐 webhook 伺服器。初次設定方式與 webhook 簽章驗證另外實作。

## 8. 第一版驗收

1. 小範圍實測兩市場來源，驗證日期、價格、成交量單位、法人合計與財報欄位。
2. 固定資料測試 KD／MACD 初始化、三個市場交易日買超及缺資料處理。
3. 測試績效跨週末／假日、未到期、停牌與公司行動；不得填零。
4. 同日重跑、發送失敗重試與狀態保存後恢復，不重複推薦或發送。
5. 本地輸出報告；Actions dry run 產生同樣內容；最後驗證真實群組發送與配額。
6. 驗收每天運行與正確追蹤，和驗收策略有預測效果，分開記錄。

若需執行超過 5 分鐘的歷史初始化、資料處理或訓練，先提供指令、預計輸出、log 與進度查核方法，交由使用者確認完成後再繼續，不持續監控。
